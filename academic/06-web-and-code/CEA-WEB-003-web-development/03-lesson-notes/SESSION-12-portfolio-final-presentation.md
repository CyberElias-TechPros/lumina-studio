## 0–10 · Review & warm-up

Three students present 20-second teasers of their builds; the room votes Gallery-vote (non-graded, full of joy).

## 10–25 · Teaching block (briefing)

**Portfolio presentation.** 3 minutes + 2 defence: who it's for · the stack tour (HTML/CSS/JS, Git, Netlify) · the interactive feature live-demo · the decision you'd revisit (honesty is currency) · what's next (WEB-001 mobile, freelance, internships).
**Project documentation.** README becomes portfolio write-up: problem → constraints → decisions → outcome → link. Export as PDF for CVs. Pin the repo on GitHub.
**Final project requirements (observed).** Live URL · ≥1 self-coded interactive feature · console-clean on assessor's machine · GitHub repo with ≥5 commits · 3-minute presentation.

## 25–80 · Final demonstrations (observed)

Per student: live load on assessor's fresh browser/machine/phone · interactive feature demo · console opened — no errors · repo walk (commit history) · README read · P1–P8 scored. Q&A: one technical ("why textContent?"), one judgement ("what did the browser teach you?").

## 80–100 · Debrief & close

Wall-of-URLs photo. Cohort WhatsApp/alumni channel. Certificates restated (gate: live + interactive, unaided). Next steps: WEB-004 WordPress for client velocity, BUS-002 freelancing to monetise, HWS-003 cyber-basics for safe deploys.

## 100–110 · Correction & check

KC12: (1) README decision section for whom. (2) Console clean means. (3) ≥5 commits shows. (4) Defence currency. (5) The one thing S12 proves.

## 110–120 · Course close

Certificates after gate passes. Keep the repo public — recruiters click.

## Answers — KC12

1. Reviewers/clients assessing judgement, not just code. 2) No uncaught errors/warnings on fresh load. 3) Process discipline — without it we only grade the photograph, not the work. 4) Reasoning + honest trade-offs. 5) You can engineer AND communicate — the employable pair.

## Homework
