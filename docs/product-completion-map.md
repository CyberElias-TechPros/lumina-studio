# Product completion map and release order

This is a working inventory, not evidence that every screen, endpoint or production record has been audited. The app has hundreds of routes and many role workspaces; successful rendering or the presence of an API does not establish that a journey is safe, complete or backed by genuine data. The current release gate is [internal-production-readiness.md](internal-production-readiness.md), and the configuration guide is [go-live-checklist.md](go-live-checklist.md).

## Dependency order

1. **Trust and recovery:** contain the reported credential incident, verify staff identities and access recovery, preserve evidence, back up and classify data, separate real data from fixtures, and verify authorization. Do not delete or reassign records based on guesswork.
2. **Core learner lifecycle:** course discovery → application → acceptance/enrollment → payment or approved offline arrangement → verified access → learning, submissions and grading → completion review → certificate. Each transition needs an authorised owner, consistent state, audit evidence, retry behavior, useful failure messages and support handoff.
3. **People and teaching relationships:** verified parent invitations; explicit, revocable teaching rosters; adult-only opt-in reviewed mentoring. These are implemented locally in part but need live-data verification, policy and operational safeguards. Existing data is not automatically trusted.
4. **Finance and service delivery:** owner-scoped invoices and client projects, payment reconciliation/refunds, receipts, handover and support. Do not unlock generic checkout for an invoice unless the server proves the payer, invoice, amount, status and provider transaction are linked.
5. **Other role workspaces:** inventory each role's activities and record ownership; replace examples with real scoped data and actionable empty states. Validate staff delegation and each list, aggregate, download and mutation with same-role and cross-role users. Role-only access does not prove ownership.
6. **Cross-cutting release controls:** accessibility, mobile and slow-network testing; notification preferences and deliverability; observability, privacy, retention, backups and restore drills; operational runbooks, provider sandbox tests, approvals and phased rollout. Keys configure integrations but cannot supply these controls.

## Definition of done for each workflow

- Map states, actors, ownership, prerequisites, approvals, invalid transitions and support/recovery paths; test the complete happy path plus empty, invalid, expired, revoked, duplicate, interrupted and concurrent cases.
- Enforce authorization and input validation on the server for reads, writes, aggregates, exports, files and realtime; test two distinct users with the same role, other roles, suspended accounts and unauthenticated requests.
- Use transaction boundaries and durable idempotency for critical state changes; explicitly separate external side effects and reconcile uncertain provider outcomes. Avoid sending private data in notifications or logs.
- Clearly distinguish configured, verified and delivered; never fabricate counts, people, approvals or payment status. Test with synthetic fixtures only in isolated environments and review actual data separately.
- Provide keyboard/screen-reader accessible states, mobile layouts, understandable errors and a staffed support path. Verify privacy notices, purpose, retention and deletion with qualified owners.
- Record exact tests, deployment version, migration/rollback plan and named approvals; monitor production after controlled rollout. Document optional or intentionally unavailable features rather than silently treating them as working.

## Adjustable defaults

Prefer centrally documented, validated settings with safe defaults and explicit limits over hard-coded business policy. Changes affecting money, access, consent, grading, eligibility or retention require an authorised actor, audit, effective time and tests; a settings screen alone is not a policy approval. Several current defaults are still code constants, including roster/mentoring expiry limits and request caps. Assignment publication references are retained without an automatic expiry until a retention policy is approved. Changing those choices requires a code change and review today.
