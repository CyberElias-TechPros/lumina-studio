# Editorial and public-content operations

This document is the working checklist for public learning notes and course pages. It is intended to keep the website useful to learners and accurate about what Cyber Elias Academy can currently deliver.

## Before publishing a learning note

- Name the specific learner task the page helps someone complete. Avoid publishing a page whose only purpose is to target a search phrase.
- Have the named author or responsible educator review the explanation and confirm that the instructions are safe to follow.
- Test software steps against the stated operating system or application version. Call out meaningful version differences instead of implying every screen is identical.
- Include an exercise, expected result or other practical way for a reader to check their understanding.
- Link to a primary or official source when a claim depends on changing rules, financial processes, health or safety advice, platform policy, or an official application process.
- Keep instructional scenarios distinct from testimonials. Never present a fictional, composite, anonymised or unverified story as measured learner progress, job placement, income or employer feedback. Obtain permission before publishing identifiable learner information.
- Use a real publication or review date only when the event has actually happened and has been recorded. Do not generate a publication schedule or set every page's review date to a shared default.

## Before publishing or changing a course page

- Confirm the title, fee, duration, timetable, prerequisites, delivery mode and final assessed work with admissions.
- Make it clear which session pages contain a full lecture and which are syllabus outlines. Do not describe an outline as a completed class lesson.
- Add a session to the public learning-resource sitemap only after its full lecture exists. Outline-only session pages should remain noindex until the full lesson is ready.
- Keep the public course finder and course-page requirements based on the same course catalogue data, not independently typed prices or schedules.

## When a correction is reported

1. Record the affected URL, the reported step, device/application version if supplied, and the date the report arrived.
2. Reproduce the issue where possible. Check the software maker's or relevant authority's current instructions for safety-sensitive or time-sensitive claims.
3. Correct the page or explain why the original instruction remains accurate. Do not ask the reporter to send passwords, one-time codes, payment details or private learner records.
4. Record a review date only after the content has actually been checked; if the wording or steps materially change, record the true modification date as well.
5. Recheck related pages and the generated sitemap when a change affects the course catalogue or publication status.

## Quality gate

A page is ready when a learner can tell who is responsible for it, what the page helps them do, what assumptions it makes, how to practise, what remains uncertain or version-dependent, and where to report a problem. If it cannot meet that bar, improve it, keep it as an unpublished outline, or consolidate it with a more useful page rather than adding another thin URL.
