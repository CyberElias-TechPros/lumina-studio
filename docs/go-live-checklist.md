# Go-live checklist: configuration is not readiness

**Status: not production-ready as a whole.** Adding API keys alone cannot validate data ownership, recover compromised accounts, establish operating policies, or prove payment and messaging delivery. The detailed incident, data-provenance and authorization release gates are in [internal-production-readiness.md](internal-production-readiness.md). Historical claims that everything is already implemented or that an operations badge proves readiness should not be used as release approval.

## Sequence and acceptance evidence

1. **Security and recovery first.** An authorised owner should address the reported shared-credential incident, establish verified administrator recovery and preserve logs. Restrict sensitive workspaces until ownership and authorization are reviewed. Take and verify backups before changes; inventory real and demo records without blanket deletion.
2. **Product and legal decisions.** Confirm academy contact details, policies, age/guardian rules, teaching rosters, course pricing, refund and certificate rules, and mentoring safeguards. Have qualified owners approve them; code assertions are not independent verification.
3. **Environment separation.** Use isolated development, staging and production accounts, databases and provider credentials. Review migrations, data provenance, release order and rollback against representative data. Never run demo seeds against real records. Older clients and backend versions may bypass newer protections; coordinate the release. The deployment automation and historical migration ledger need independent review rather than blind execution.
4. **Configure integrations securely.** Only public values belong in browser-exposed `NEXT_PUBLIC_*` variables. Set backend secrets in the runtime provider's secret store; never commit them, paste them into chat, include them in logs, or put them in a `NEXT_PUBLIC_*` value. GitHub Actions encrypted secrets are available to workflows explicitly referencing them; adding an entry there does **not** automatically configure the frontend or backend runtime. Grant deployment access narrowly and rotate exposed credentials.
5. **Exercise staging end to end.** Use isolated, permissioned test accounts: sign-up, verification, login/MFA and recovery; admissions/enrollment; course access, assignments and grading; certificates; parent links; reviewed mentoring; client support and any enabled role. Check same-role cross-user access, revoked/expired permissions, failures and retries. Verify payment checkout, webhook signatures, reconciliation, duplicates, refunds and receipts with provider test credentials before real transactions; independently verify mail, SMS and push delivery and consent. Mock-backed browser tests do not prove provider delivery or correct live records.
6. **Operational approval and monitoring.** Confirm support ownership, escalation and incident response, accessibility and device testing, retention/deletion and data-subject request procedures, monitoring/alerts, audit-log protection and a tested recovery drill. Record named product, security, finance and privacy approvals. Enable each workflow only after its particular gates pass; review actual production accounts and data separately.

## Configuration inventory (names only)

Refer to `.env.example` for browser-exposed settings and `backend/.dev.vars.example` for server-side integration names. The runtime and deployment owners must determine which services are required for the approved release. In particular:

| Capability                 | Public frontend value                                            | Backend/provider secret or setup                                                                                                           |
| -------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| API connection             | `NEXT_PUBLIC_API_URL`                                            | Independently verify the correct API origin and authorization                                                                              |
| Email and account recovery | None                                                             | `EMAIL_API_KEY`, verified sending domain and delivery testing                                                                              |
| Payments                   | `NEXT_PUBLIC_PAYSTACK_PUBLIC_KEY` if required by the chosen flow | `PAYSTACK_SECRET_KEY`, correct webhook registration and reconciliation tests                                                               |
| Bot protection             | `NEXT_PUBLIC_TURNSTILE_SITE_KEY`                                 | `TURNSTILE_SECRET_KEY`, matching widget/origin configuration                                                                               |
| Browser push               | `NEXT_PUBLIC_VAPID_PUBLIC_KEY`                                   | Matching VAPID keys, consent and actual delivery verification                                                                              |
| SMS, AI, error reporting   | No private keys in the browser                                   | Optional server credentials and reviewed service-specific policies; some AI functions intentionally remain unavailable outside development |

Do not put actual values in this document, source control, a ticket or chat. Configure test and production credentials separately, restrict access, and document who can rotate them. A successful build, configured secret, health response or status badge is not proof that these journeys work or that the app is secure. See [internal-production-readiness.md](internal-production-readiness.md) for known unfinished areas and release cautions.
