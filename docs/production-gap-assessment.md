# Production-readiness assessment: prioritized work

This is an initial code-based assessment, **not** a complete audit of every role, production account or provider. The repository contains hundreds of routes and many role workspaces. A build or passing tests does not establish end-to-end readiness, data provenance, security, legal compliance or real-world delivery. See [product completion map](product-completion-map.md), [internal production readiness](internal-production-readiness.md), [go-live checklist](go-live-checklist.md) and [Afkit plan](afkit-dropshipping-plan.md) for existing detail. Current changes are local to the working branch unless independently deployed.

## Immediate findings and actions

| Priority | Area / user journey | Evidence and next action |
| --- | --- | --- |
| Critical | Security and recovery | A shared credential was previously reported compromised; verified containment, identity recovery and incident review have not been established. An authorized owner must contain and investigate, preserve logs, rotate affected credentials and test administrator recovery without sharing secrets in chat. Check backups and migration ledger before changes. |
| Critical | Realtime chat and live classes | This branch adds explicit expiring chat memberships, audited admin grant/revoke APIs, origin and session checks, and fan-out of only the sender’s persisted chat message. This branch disables that endpoint for all environments and makes learner and legacy mentor screens explicitly read-only; old clients will receive 503 rather than a false success. Existing records remain unchanged and past delivery is unknown. This is a safety stop, **not a working replacement**. Other messaging/chat endpoints have not been audited as part of this change. |

## Sequence for a real release

1. Contain the reported credential incident; establish verified admin access and backups. Inventory real data versus examples and independently verify the deployment/migration state.
2. Choose a small release scope and responsible owner for each journey; document the actor, ownership and consent, state machine, failure/retry/recovery paths and policy. Do not assume all workspace roles are production-safe because screens render.
3. Implement real participant-authorized messaging before enabling send: identity and membership model, transactional durable messages, recipient visibility, ownership and revocation, abuse/rate controls, moderation/safeguarding, privacy/retention, notification preferences, idempotency and reconciliation. Test two accounts, unauthorized users, revocation, duplicate requests, outages and concurrent sends. Review how legacy rows will be handled; do not infer recipients from displayed names or silently deliver past text.
4. Build each remaining journey as a tested vertical slice; verify both same-role ownership and cross-role denial, invalid and duplicate transitions, concurrency and operational recovery. Complete physical commerce separately with authoritative snapshots, payment and fulfillment state, supplier handoff and reconciliation.
5. In isolated staging, test integrations with their providers, audit actual data and migration compatibility, rehearse restore and rollback, document named product/security/finance/privacy/support approvals, and deploy a limited release with monitoring. Expand only after observed results.

No live user, payment, supplier order, external account, production deployment or migration has been changed by this assessment. A complete app-wide production signoff remains outstanding.
