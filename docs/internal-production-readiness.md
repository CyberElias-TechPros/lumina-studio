# Internal production readiness — investigation and release gate

Status: **not production-ready as a whole**. This is a source and repository-history investigation, not a live database, account, authorization or production-environment audit. It does not establish which demo rows or accounts currently exist. An API reading a database does not prove its contents are real or user-scoped. Do not use the older blanket remediation claim in `docs/audit-mock-data-gaps.md` as signoff.

## Immediate owner actions

1. An authorised operator should urgently check whether any historical demonstration accounts still exist or can authenticate, including privileged accounts. The historical deployment log in `docs/role-gap-matrix.md` records demo accounts and seed data being deployed in the past; it is not evidence of their current status. Disable confirmed demonstration access, revoke active sessions and rotate any affected credentials using the normal incident process. Avoid copying demo credentials into tickets or chat. Verify that genuine staff retain access.
2. Restrict access to sensitive internal workspaces until the server-side authorization and record ownership review below has been completed. A client-side page change is not an access-control boundary. Assess exposure, audit logs and any notification obligations with the security/data-protection owner.
3. Take a verified backup and inventory records with provenance before any cleanup. Classify demo rows and dependencies separately from real enrollment, finance, messages and user records. Approve a reviewed, reversible cleanup and test it in isolation first. Never run blanket deletes or remote demonstration seed scripts to solve this.

These are code changes only, not evidence that production is configured or deployed; validate payment flows and AI policy independently before use.
- The `db:seed:demo:remote` npm shortcut is intentionally blocked; this is a guardrail, not a database policy. A direct database command or other remote seed can still insert fabricated rows. Existing local fixtures are retained for isolated development and testing.

## Required before reopening or declaring ready

- Replace examples with correctly scoped records, explicit empty/error states, or a clearly unavailable feature; remove nonfunctional controls and unverified personal or financial claims. Audit AI and payment failure modes, privacy, data retention, authentication, backups and restore drills.

Validate actual production account and database state separately. A successful UI build, mock-backed browser suite or deployed API alone is not production signoff.

## Course assessment limitation

The public Quick Challenge currently consists of one question on each of five beginner Computer Basics notes. The separate four-prompt course finder includes two basic computer questions and maps interests to 13 course pages. Neither is a course-specific test or a reliable prerequisite assessment. Build prerequisite maps from CEA-approved course requirements, author and independently review multiple questions and practical checks per relevant prerequisite, and validate their quality before presenting readiness or placement conclusions. Avoid inventing course requirements, scores or passing thresholds.

## Certificate integrity and recipient directory (local only)

The former issuance endpoint accepted an arbitrary active user, course slug and title without proving enrollment, completion, eligibility or authorized issuer relationship. Local migration `0074` and matching code replace the pause with an admin-only manual-review workflow: an administrator selects an active enrolled student and a real course, records a review reference, and explicitly attests that the academy's requirements were checked. The canonical course title is used; enrollment is a prerequisite, not proof of completion. Issuance, review reference and audit event are transactional; an unrevoked record blocks a duplicate, including a legacy record. An administrator can revoke a reviewed or legacy record with a reason and later issue a reviewed replacement. Public lookup reports a revoked code as invalid; learners see revocation status, and evidence and revocation reasons are admin-only. Portal summaries exclude revoked records. Older backends do not honor the new revocation table, so coordinate rollback carefully: a rollback could make revoked codes appear valid again. Review references must not contain sensitive personal information. Audit events are stored separately from certificates, but a retention policy and independent tamper-resistant audit are not yet in place.

This is a manual administrative attestation, not an automated or independently verified eligibility decision. CEA still needs to define its actual completion rules, reviewer authority, evidence procedures, retention and support/dispute process before using it for official credentials. Previous records are retained and labelled legacy; public lookup reports a legacy registry match, not proof of completion or identity. Seeded/test records and existing record provenance must be reviewed before any real registry launch. Instructor access to the global account directory remains blocked. The owner view shows at most 100 records and warns if truncated; admin review shows at most 100 per learner/course and prevents issuing when truncated. Code lookup does not prove a holder's identity. No certificates have been issued, deleted or revoked in production.

Web push previously allowed instructors to target arbitrary user IDs even without the directory. Local changes limit cross-user web push to administrators and preserve self-targeting for other authenticated users. Instructor-targeted communication requires a verified teaching relationship before it can be restored. UI controls reflect these limitations. These changes require rollout and integration review and have not been deployed.

## Guardian invitations and web push (local only)

Apply migrations `0070_web_push_session_binding.sql`, `0071_parent_invitation_recipient.sql`, `0072_verified_parent_links.sql`, `0073_assignment_rosters.sql` and `0074_certificate_review.sql` before deploying the matching backend. Back up and test the migrations and rollback/restore process in isolation first. These changes are not deployed.

New guardian invitations are issued by administrators to a selected, active parent account and active student account. The administrator must independently verify the relationship; verified email demonstrates account control, not guardianship. The administrator must privately share the generated link; the system does not send it automatically. Public previews omit names and notes. New bearer tokens are stored as SHA-256 lookup keys rather than usable tokens. Old plaintext tokens remain stored until an approved retention/cleanup process and cannot be redeemed; any previously issued plaintext links must be reissued, including links created by an earlier version with a bound recipient. A rollback to an older backend cannot redeem new hashed links; plan a coordinated rollout and reissue if necessary. Redemption requires the intended active parent account with verified email; it does not change a user's role. Legacy invitations without a bound recipient cannot be redeemed and must be reissued after verification. The parent should sign in to the intended account, verify its email if needed, and return to the invitation. The same tab preserves the link through password, MFA and email verification; if a magic link opens in a different tab or device, reopen the invitation there after sign-in. A token remains sensitive: avoid logs, browser history exposure and untrusted sharing. Existing `parent_students` relationships have unknown provenance and are not trusted by parent reads or parent portal aggregates under migration 0072. They are retained, not deleted; affected parents lose access until an administrator independently verifies each relationship and issues a new invitation to the correct parent account. Acceptance re-verifies an existing link atomically. Plan family communication, recovery and access support before rollout. Existing relationships and production account data have not been reviewed. Invitation flows were tested against isolated fixtures, not live accounts.

Push registration and sends now require JSON and use best-effort per-user KV throttles (60 registrations and 30 sends per hour); this KV counter is eventually consistent and non-atomic, so it is not a hard abuse or cost boundary. Sends fail closed above 50 stored subscriptions for a target, including old/unbound rows; an authorized review and cleanup process is needed for affected accounts. Use an atomic limiter and egress controls before relying on this as abuse protection. Push endpoints are restricted to selected browser-service HTTPS hosts, checked at registration and send time, with redirects disabled and cross-account endpoint reassignment denied. Subscriptions are now bound to the registering session; unbound legacy rows and expired, revoked, MFA-pending or suspended-account sessions are skipped, not deleted. They need re-registration from an eligible session. Web push sends a generic inbox hint, including to older browser workers; custom caller text and URLs are not delivered and the hint does not create an inbox message. Saved app-notification opt-out and Lagos quiet hours are respected. Each web-push endpoint is rechecked against its session and stored key after encryption and just before network handoff. Push TTL is zero to avoid storing messages for later delivery: offline browsers may miss notifications. A send already handed to a push provider cannot be recalled if logout or suspension occurs concurrently, and provider acceptance does not prove device delivery; avoid sensitive notification content. Background refresh no longer requests browser permission. A notification-page control requests it explicitly and surfaces account conflicts; a confirmed local reset can unsubscribe this browser and register a fresh endpoint without deleting another account's server record. Reset can stop notifications for a different account using the same browser. Browser/provider compatibility, logout/account-switch recovery, live delivery and network egress controls still need independent review before rollout. The allowlist is not a substitute for network controls. No production data or accounts were changed.

## Instructor course authorization (local only)

Course titles are not reliable identifiers or evidence of a teaching relationship. Migration `0073` introduces an empty, explicit instructor–student–course roster: an administrator independently confirms each relationship through User management, selects an expiry within one year, and can revoke it. Grant and revocation changes are transactionally recorded in `assignment_roster_events`. Instructor publishing now uses only active, unexpired grants for currently active student accounts with a matching enrollment; no legacy titles or relationships are automatically promoted. A grant is a recorded administrative assertion, not independent proof; staff must verify and maintain each roster. Expiration and revocation stop future publishing but do not withdraw previously assigned work or the recorded author's access to past submissions and grading. A grant can become effective again if an account is reactivated or an enrollment recreated before expiry; revoke it when the relationship ends. Existing legacy assignment owners and provenance have not been independently validated, and other instructor actions still require review. The UI lists at most 200 instructor courses and warns if more exist. No migration or roster change has been applied to production.

Instructors can publish via the assignment center after an administrator explicitly grants roster access; the roster administration and publishing interfaces and API have been tested with isolated fixtures, not real accounts. Grant management is per learner, not a bulk roster or cohort workflow. There is no automated expiry notification, identity verification, audit-log viewer or historic-access revocation; these remain operational and product requirements.

Administrator publishing now inserts all eligible course-enrollment assignment rows and in-app notifications in one D1 batch transaction. Eligibility is limited to active accounts currently marked student, not a verified cohort: enrollments have no status, cohort or instructor association, so the roster can still include learners who should no longer receive work. Publication fails closed for an empty eligible roster or over 500 recipients; the cap needs production capacity and workflow review. SMS hints are generic, best-effort, concurrency-limited and outside the transaction: provider acceptance does not prove delivery. Migration `0076` adds an author-scoped, transactional publication reference: retries with the same UUID and normalized details return the original result; mismatched reuse fails, and concurrent duplicates do not create a second group or in-app notifications. The instructor UI saves a reference and content fingerprint in the current browser tab and can check a committed result after reload. A missing result does not prove that a request is not still in flight. References are retained without an automatic expiry pending an approved retention policy. Older clients that omit a reference still use legacy one-shot behavior and can duplicate on retry; different tabs/devices or clearing browser storage do not share recovery state. SMS remains best effort outside the transaction and is not retried on replay. The migration and flow have not been deployed or tested with live records. Instructors cannot move a group's deadline if any row has a different or missing recorded creator; admins can still change legacy groups and must review their provenance. Recorded creators alone are not independently verified, and these changes neither repair existing groups nor establish a cohort model.

## Reviewed adult mentoring (local only)

Migration `0075` creates new, isolated eligibility, profile, consent, request and audit tables. Legacy seeded directory and dashboard rows are **not** imported or treated as proof of consent or screening. In the new flow an administrator records an independent adult eligibility check and reference (maximum one year); a mentor/alumnus opts in with a minimal profile; an administrator separately reviews and approves that exact revision. Editing, withdrawal, or changing eligibility removes approval. Eligible adult students/alumni can request a reviewed profile. The mentor can accept or decline; either party can cancel. Role, ownership, active account, eligibility and profile state are checked server-side; creation is capped at ten requests per learner per hour and 50 pending per mentor, with one active request per pair. Events and generic notifications are transactional. The UI does not arrange meetings or exchange contact details; the academy must coordinate. Demo mode starts empty and does not simulate successful writes. Limits and consent version are currently code defaults, not administrator settings.

**This is not a substitute for operational safeguarding or legal compliance.** No independently verified age, identity, background screening, training, consent-policy text, complaint/incident response, monitoring, retention/deletion process or meeting coordination is supplied by this implementation. References and administrator attestations are assertions, not verification. Adopt documented, jurisdiction-specific legal and safeguarding policies and confirm who performs checks before enabling real mentoring; do not use this flow for minors. Database event logs share the same trust boundary as application data and are not tamper-resistant. Establish access controls, backups, retention and external audit/monitoring. Expired/revoked eligibility prevents new requests and acceptance but does not delete historical records or terminate any offline relationship; staff need a follow-up process. Request notifications are best-effort product notices, not a guarantee of delivery.

The defaults were informed by [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Patterns_Cheat_Sheet.html), [ICO consent guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/lawful-basis/a-guide-to-lawful-basis/consent/) and [youth mentoring safeguarding guidance](https://youth.gov/youth-topics/mentoring/best-practices-mentoring-relationships-and-programs). These are design references, not legal advice or evidence of compliance with Nigerian law.

Before rollout, review migrations `0070`–`0076`, schema compatibility, backup/restore and staged deployment against representative data, test access and account status in the target environment, and train staff. Deploy the new API and migration together; older releases can expose legacy seeded profiles or permit flows without the new controls. Rollback requires disabling the directory/requests or retaining equivalent safeguards and coordinating clients, rather than blindly reverting. No production migration, live-data validation, operational review or deployment has been performed.
